# 05 Security controls

**What this is:** the controls that protect GRIT Hub Learning, its learners' data and the integrity of assessments, with where each one is enforced and how it is tested. Written for QCTO and quality-partner evaluators, GRIT Hub management and the Information Officer.

Every control below is enforced on the server. Hiding a button is never the control.

## 1. Sign-in: passkeys and multi-factor policy

| Control                      | Detail                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No passwords                 | Nobody has an LMS password, so there is nothing to phish, reuse or leak.                                                                                                                                                                                                                                                                     |
| Passkeys (WebAuthn) first    | A passkey is a key pair held on the person's device. Sign-in needs **the device (something you have) plus its fingerprint, face or screen lock (something you are or know)**: the LMS requires user verification on every passkey sign-in and registration (`userVerification: "required"`), so a passkey sign-in is multi-factor by design. |
| No biometric data            | The fingerprint or face check happens on the device. The LMS stores only a public key ([04 §3.1](04-popia-pack.md#31-accounts-sign-in-and-activity)).                                                                                                                                                                                        |
| Phishing resistance          | Passkeys are bound to the LMS domain (`WEBAUTHN_RP_ID`); a look-alike site can't use them.                                                                                                                                                                                                                                                   |
| Email links (main sign-in)   | Since 2026-11-11 the main way in: single-use sign-in links (15 min) to the registered email, used on a button press (POST) so link scanners can't spend them. After the link: no passkey → prompted to add one; has a passkey → asked to confirm it (`/auth/confirm`, audited as `auth.passkey.confirmed`), which anyone may skip. A link sign-in is a full sign-in; the passkey can also be used directly ("Sign in with passkey"). |
| Step-up for privileged roles | **SDP admins, assessors and moderators must have an active passkey** to open their screens or perform their actions (`STEP_UP_ROLES` in `lib/access.ts`, checked by the proxy and again by `authorize()` in every action). Without one they are sent to add a passkey, and the attempt is audited.                                           |
| Recent re-authentication     | Not required yet: step-up checks that a passkey exists, not that it was used recently. **TODO(T-24)** (deferred by the product owner on 2026-11-07).                                                                                                                                                                                         |
| Sessions                     | Random 256-bit token in an `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` cookie; only its SHA-256 is stored; 14-day maximum; revoked on sign-out, deactivation and recovery.                                                                                                                                                               |
| Account recovery             | Email link, or admin-verified recovery (identity checked in person, by video with ID, or by calling a number on record); all passkeys and sessions are revoked first. No SMS codes.                                                                                                                                                          |
| First SDP admin              | Created once per deployment by `yarn workspace lms admin:bootstrap` (`lib/server/bootstrap.ts`): refuses if an SDP admin exists, audited as `admin.bootstrap.sdp_admin` (ids only), tested in `test/bootstrap.test.ts`. |
| Invite-only                  | No public sign-up. Invitations are single-use (72 h).                                                                                                                                                                                                                                                                                        |
| Rate limits                  | Every sign-in entry point is rate limited per IP and per email (`lib/server/ratelimit.ts`), counted in Postgres so limits hold across servers. Breaches are audited.                                                                                                                                                                         |
| Service accounts             | Staff accounts on Vercel, the database host, GitHub, Mux, Resend and Airtable must use MFA. **TODO(T-26)**.                                                                                                                                                                                                                                  |

Enforcement in three layers, each tested:

1. **Route rules** (`lib/access.ts`, applied by `proxy.ts` to every request; `test/access.test.ts`, `test/proxy.test.ts`). Denials are audited.
2. **`authorize()`** in every server action that writes (`lib/server/auth.ts`), plus cohort scoping in the data layer (`lib/server/staffScope.ts`).
3. **Database rules** (triggers and constraints, `packages/db/README.md`): for example, a moderator can't moderate their own decision, a cohort has one assessor, external evaluator grants must expire.

Separation of duties: one assessor per cohort; a moderator never moderates their own decision; appeals are decided by someone other than the assessor; SDP admins and facilitators never see answer keys.

## 4. Audit log

- **What is recorded:** sign-ins and failures, link requests, passkey changes, recovery, permission denials, rate-limit hits, consent, profile changes (field names only), invitations and imports, every assessment event (start, submit, auto-submit, pause, extra time, unlock, attendance, ID check, marks, decisions, moderation, release, appeals), practical evidence added, rejected and viewed, communication events, Form 5 changes, every export and file view, and every page an external evaluator opens. The full list is `AuditAction` in `apps/lms/lib/server/audit.ts`.
- **What is never recorded:** names, emails, ID numbers, answers, message text, file contents or CSV contents. IP addresses are stored only as a keyed hash (HMAC).
- **Integrity:** append-only. A database trigger rejects UPDATE, DELETE and TRUNCATE, and the runtime database role has no UPDATE or DELETE grant on it.
- **Reading it:** no viewer screen yet (**E-02**); custodians query it, and specific entries feed the evidence pack (for example export hashes).

## 6. Question-bank and randomisation integrity

The aim: every learner gets equal curriculum coverage, papers differ between learners, a refresh never changes a paper, answers can't be read from the browser, and any attempt can be replayed exactly (`docs/lms/randomization.md`, ADR-007, ADR-008, ADR-012).

| Control                             | Detail                                                                                                                                                                                                                                           | Test                                                                                                                                                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Equal coverage                      | Blueprints draw a fixed number of questions per curriculum component; publishing checks banks are big enough and every component is covered.                                                                                                     | `test/paper.test.ts`, coverage report                                                                                                                                                                                                                   |
| Seeded, persisted draws             | Each paper is drawn on the server with a seed from the learner, item and attempt number, then **stored** (question version, option order, option tokens, seed). Refresh, resume and other devices read the stored paper.                         | `test/assessments.test.ts`, `test/randomization.test.ts`                                                                                                                                                                                                |
| Answer keys never reach the browser | While writing, the browser receives question text and opaque option tokens only: no option ids, correctness, explanations or rubrics. Grading is on the server. Summative keys are never shown to learners. Pages holding papers are not cached. | `test/assessments.test.ts`, `test/sectionCheck.test.ts`, **`test/answerKeyBoundary.test.ts`** (2026-11-10: learner routes can't import staff key modules; client components can't import server modules; learner client code never mentions key fields) |
| Forged answers rejected             | Only tokens served for that question are accepted; inherited object keys (`__proto__`, `constructor`) are rejected too (fixed 2026-11-10).                                                                                                       | same                                                                                                                                                                                                                                                    |
| Immutable question versions         | Once a version is served, the database rejects any change to it, its options or its rubric. Edits create a new version.                                                                                                                          | `packages/db/test/question-versions.test.ts`                                                                                                                                                                                                            |
| Frozen attempts                     | Served items can't change or be deleted; responses freeze when the attempt is submitted; time limits and auto-submit are enforced on the server.                                                                                                 | `packages/db/test/assessments.test.ts`                                                                                                                                                                                                                  |
| Summatives in person only           | Papers open only after the assessor records attendance and an ID check and unlocks the paper for that learner (with a passkey). The register sign-off is final.                                                                                  | `test/assessorWorkflow.test.ts`                                                                                                                                                                                                                         |
| Exact replay                        | Moderators and evaluators see the exact paper and option order served; an exact PDF can be exported (audited).                                                                                                                                   | `test/moderation.test.ts`                                                                                                                                                                                                                               |
| Decisions and release               | Decisions are append-only; changes create a new decision. Results are released only when the moderator closes the batch.                                                                                                                         | `packages/db/test/decisions-moderation.test.ts`                                                                                                                                                                                                         |
