# POPIA: what the LMS collects and how

Status: **draft**. It must be reviewed by GRIT Hub's Information Officer before real learners are invited. The learner-facing notice text lives in `apps/lms/lib/popia.ts` (versioned; currently `2026-11-draft-1`).

## Biometric data: we never receive or store it

Passkeys (WebAuthn) use the person's own device to check a fingerprint, face or screen lock. **That check happens entirely on the device.** The LMS never receives, processes or stores biometric data of any kind: no fingerprints, face scans or templates.

What the LMS stores for each passkey (`passkey_credentials`):

| Field                                    | What it is                                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------------------- |
| credential id                            | A random identifier generated by the device                                        |
| public key                               | A public key; it can verify signatures but cannot recreate any biometric or secret |
| signature counter                        | A number the device increments, used to detect cloned authenticators               |
| transports                               | How the device connects (e.g. `internal`, `usb`)                                   |
| device label                             | A name the person chooses, e.g. "Work laptop"                                      |
| created / last used / revoked timestamps | For the person's own passkey list and the audit trail                              |

The WebAuthn "user handle" sent to devices is the user's internal UUID. It contains no name or email.

## Personal information processed by authentication and onboarding

| Data                                   | Where                      | Why                                                                                     | Notes                                                                                                   |
| -------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Name, email                            | `users`                    | Account, invitations, sign-in links                                                     | Email is the sign-in identifier                                                                         |
| Account status                         | `users`                    | Invited / active / deactivated                                                          | Deactivation blocks all access immediately                                                              |
| Notice acceptance                      | `consent_records`, `users` | Proof of which notice text was accepted, and when                                       | Stores version + SHA-256 of the exact text + timestamp; append-only                                     |
| Sessions                               | `sessions`                 | Keeping people signed in (14 days max)                                                  | Only a hash of the session token is stored; HMAC of the IP                                              |
| Sign-in, invitation and recovery links | `auth_tokens`              | Single-use emailed links                                                                | Only a SHA-256 hash is stored; 15 min (sign-in), 30 min (recovery), 72 h (invitation)                   |
| Rate-limit counters                    | `rate_limit_buckets`       | Abuse protection                                                                        | Keys are HMACs of IP/email, never the raw value                                                         |
| Audit log                              | `audit_log`                | Accountability (sign-ins, passkey changes, recovery, permission denials, admin actions) | Payloads hold ids, counts and reasons, **not** emails, names or CSV contents. IP stored only as an HMAC |
| CSV imports                            | not stored                 | Bulk invitations                                                                        | Parsed in memory; only valid rows become users; file contents are never logged or audited               |

## Consent and notice changes

- Learners accept the notice during first-time setup (step 2 of 3). Without acceptance they can't use the LMS.
- Any wording change requires a **new version string**. Users whose accepted version differs are sent back through setup to accept the new notice.
- `consent_records` is append-only (database trigger), so acceptances can't be edited or deleted.

## Account recovery

There are no SMS codes. Recovery is either:

1. **Self-service:** a magic link to the registered email address, or
2. **Admin-verified:** an SDP admin verifies identity (in person with ID, video call with ID, or a call to a number already on record), records the method and a reason, and starts recovery. All the user's passkeys and sessions are revoked, and a 30-minute single-use link is emailed. Every step is audit-logged with the admin's id.
